# Terminal Gateway — архитектура единого терминального шлюза (v0.22.0)

> Статус: реализовано в v0.22.0. Владелец архитектуры: POLER Engineering Core.
> Связанные документы: `TERMS.md` (лицензионная модель), `docs/native-retrieval-analysis.md`
> (grep/chunk), аудит v0.21.1 (`scripts/audit_stress.py --hardened`).

## 1. Концепция и место в системе

POLER Engine исторически состоит из двух поверхностей:

- **Нижний сервисный слой (Service Substrate)** — веб-GUI / Auth Companion,
  WebLens MV3, MCP-HTTP-сервер (`--mcp-http`), notebooklm-мост. Это фоновые
  сервисы: они держат сессии, токены и браузер, но не управляют рабочим
  процессом пользователя.
- **Прикладные CLI-режимы** — флаги `--grep`, `--chunk`, `--crawl`, `--impact`,
  `--shell` (внутренний REPL по web-index/notebooklm).

v0.22.0 добавляет **третий, верхний уровень** — **Terminal Gateway**
(`poler-engine --gateway`): единое окно терминала, в котором пользователь
работает и с движком, и с хостовой ОС, не покидая процесс. Gateway — это не
очередной режим поиска, а **рабочее место**: командная строка, из которой
управляется всё остальное, включая сам Service Substrate.

```
┌────────────────────────────────────────────────────────────┐
│  Terminal Gateway (REPL, --gateway)  ← ВЕРХНИЙ УРОВЕНЬ      │
│  двойной контур исполнения + конвейеры + service/attach     │
├────────────────────────────────────────────────────────────┤
│  Engine Native: search · grep · chunk · crawl · impact ·    │
│  nlm · notes · sources · gh/gl/gt/gix · benchmark · license │
├────────────────────────────────────────────────────────────┤
│  Service Substrate (НИЖНИЙ СЛОЙ): MCP-HTTP · WebLens ·     │
│  Auth Companion — управляются из gateway: service/attach    │
└────────────────────────────────────────────────────────────┘
```

## 2. Модель исполнения — двойной контур с приоритетом движка

Каждая строка ввода парсится в **конвейер** (сегменты через `|`), затем каждый
сегмент классифицируется ровно одним из двух контуров. Порядок проверки —
строгий, приоритет движка не обходится наличием одноимённого бинарника в PATH
(у пользователя почти всегда есть `/bin/grep` — но внутри gateway `grep` всегда
означает POLER Native Grep; это осознанное решение, подтверждённое бенчмарком
v0.21.0: 3.3 мс против 6.3 мс у ripgrep при полной полноте).

### Контур 1 — Engine Native (Приоритет 1)

Команда исполняется **внутри процесса движка**, без спавна внешних процессов.

Распознаётся по первому токену сегмента (опциональный префикс `poler` /
`poler-engine` срезается: `ls | poler chunk` ≡ `ls | chunk`):

| Команда | Реализация |
|---|---|
| `search` / `web`, `stats`, `nlm`, `notes`, `sources`, `sync`, `set`, `crawl`, `impact`, `gh`, `gl`, `gt`, `gix` | делегация в `shell::commands::dispatch` (внутренний REPL v0.15+, тот же код — один источник правды) |
| `grep PATTERN [--regex] [-i] [-A N] [-B N] [--count] [--list] … [--stdin]` | `retrieval::grep_run` + `render_text` (v0.20.0); `--stdin` — поиск по буферу из пайпа вместо файлов |
| `chunk [PATH] [--size N] [--overlap N] [--json] [--stdin]` | `retrieval::chunk_document` (v0.20.0); без PATH и в конвейере — чанкование stdin |
| `benchmark [--json PATH]` | `bench::run_suite` (v0.21.0) |
| `service start/stop/status/attach`, `attach` | §5 |
| `license`, `cd`, `pwd`, `clear`, `help`, `version`, `quit` | служебные команды gateway |
| `weblens [start/stop/status]` | сахар над `service` (WebLens — сервис) |

### Контур 2 — Controlled Host OS Proxy (Приоритет 2)

Всё, что не опознано как команда движка, исполняется **в хостовой ОС**
(Linux/macOS) через `std::process::Command` — но строго через
**Sandboxed OS Subshell** (§4): политика безопасности → контролируемый спавн →
кап вывода → таймаут → перехват SIGINT. Явный синтаксис принуждения: `!cmd`
или `host cmd` (например `!grep`, чтобы вызвать системный grep, а не движковый).

### Почему не «спавнить настоящий shell»

`sh -c "<строка>"` отдал бы строку на парсинг `/bin/sh` со всеми его
возможностями (подстановки, `$(...)`, бесконечная рекурсия), и sandbox свёлся
бы к проверке исходного текста. Вместо этого gateway сам токенизирует строку
(кавычки `'…'`/`"…"` поддерживаются, подстановки — нет) и запускает бинарник
**напрямую** (`execvp`-семантика), без промежуточного shell. Это устраняет
целый класс инъекций: `echo $(rm -rf /)` не исполняется вовсе — токен `$(rm…`
просто не найден как программа.

## 3. Конвейеры (pipes)

Сегменты конвейера нумеруются слева направо; вывод каждого сегмента (строка)
становится stdin следующего. Смешивание контуров разрешено в любом порядке:

```
ls -la src/ | chunk --size 200          # host → engine: чанкование вывода ls
cat src/main.rs | impact main           # host → engine: impact по символу
grep "fn " --stdin | wc -l              # engine → host: подсчёт движкового grep
cat README.md | chunk --size 300 | grep POLER --stdin --count
```

Правила:
- Engine-сегмент в середине/конце конвейера получает данные предыдущего
  сегмента в `stdin: Option<String>`.
- `grep`/`chunk` поддерживают флаг `--stdin` (в конвейере включается
  автоматически, флаг — для явности).
- `impact SYMBOL` в конвейере: код из stdin пишется во временный файл
  (`std::env::temp_dir()`), для него строится SymbolTable, отчёт печатается
  в stdout конвейера.
- Редирект `>` / `>>` / `2>` применяется к финальному выводу конвейера.
- `cd`/`pwd`/`set`/`service`/`license`/`quit` не участвуют в конвейерах
  (ошибка парсинга — как в bash для builtin в pipe, где это осмысленно).

## 4. Sandbox OS Subshell — политика безопасности

### 4.1 Категории решений

`Policy = Allow | Confirm(reason) | Block(reason)`:

- **Block** — деструктивные/системные операции, отказ сразу, без вопросов:
  - `rm` с `-r`/`-f` по корневым/системным целям (`/`, `/usr`, `/etc`,
    `/bin`, `/sbin`, `/lib*`, `/boot`, `/sys`, `/proc`, `/dev`, `/var`,
    `/home` верхнего уровня, `~` целиком, сам cwd `.`/`..`);
  - форк-бомбы — сырой скан строки на `:(){` (варианты с пробелами
    нормализуются) в любом месте конвейера, включая `bash -c '…'`;
  - `dd` с `of=/dev/…`, `mkfs*`, `wipefs`, `fdisk`, `parted`, `sfdisk`;
  - `shutdown`, `reboot`, `halt`, `poweroff`, `init 0/6`, `systemctl
    poweroff/reboot`;
  - редиректы в блочные/системные устройства (`> /dev/sd*`, `> /dev/nvme*`,
    `> /dev/disk*`) и в системные каталоги (`> /etc/…`, `> /boot/…`,
    `> /sys/…`, `> /proc/…`);
  - `chmod -R`/`chown -R` по системным корням;
  - удалённое исполнение `curl … | sh|bash` / `wget … | sh|bash`;
  - `mv`/`cp` с целью в `/dev`, `/sys`, `/proc`.
- **Confirm** — интерактивное подтверждение yes/no (в non-tty и в конвейере
  без `--yes` — отказ): `sudo`/`su`/`doas`/`pkexec` (эскалация прав);
  `rm` с рекурсией по НЕсистемным путям (показываем цели); `dd` без
  `/dev`-цели; `kill -9` не-своих процессов не поддерживаем — kill вообще
  вне gateway (используйте service stop).
- **Allow** — всё остальное: `ls`, `cat`, `git`, `cargo`, `python`, …

### 4.2 Честная threat model

Sandbox gateway — **политический** (userspace-фильтр), а не ядровый
(seccomp/namespace/sandbox-exec не подключаются — принцип нуля новых
зависимостей движка). Что это значит:

- Гарантируется: ни одна строка не достигает exec без классификации;
  разбор делаем мы, а не `/bin/sh`; спавн — прямой (`Command`, без shell);
  вывод ограничен (`OUTPUT_CAP` = 16 МБ на поток, как CDP-кап из аудита
  v0.21.1); таймаут стены (`HOST_TIMEOUT` = 120 с по умолчанию,
  `set hosttimeout N`); переменные окружения фильтруются (см. 4.3).
- НЕ гарантируется: изоляция эксплойта самого запускаемого бинарника
  (злонамеренная программа обходит любые пользователю доступные механизмы
  своей жертвы) — для этого нужны ядровые песочницы, и это явно указано
  как ограничение. Gateway защищает от **ошибок пользователя**
  (rm -rf по неверному пути, случайный fork-bomb из туториала, слив
  секретов в дочерние процессы), а не от целенаправленного малваре.

### 4.3 Контроль окружения дочерних процессов

Дочерним процессам передаётся **минимальное окружение**: `PATH`, `HOME`,
`LANG`, `LC_*`, `TERM`, `TMPDIR` и полностью унаследованный
`POLER_*`-неймспейс **кроме** секретов. Вырезаются все переменные, чьи имена
содержат `TOKEN`, `SECRET`, `PASSWORD` или заканчиваются на `_KEY`/`_KEYS`.
Дополнительно выставляется `POLER_GATEWAY=1` (дочерний процесс может
детектировать, что он в субшелле). Полный набор окружения — через
`set hostenv full` (по умолчанию `filtered`; изменение фиксируется в
строке статуса). Обоснование: рефреш-токены Google и MCP-токен живут в
файлах 0600 (аудит v0.21.1), но если пользователь экспортировал секрет в
env основного процесса — он не должен утекать в каждый `ls`.

### 4.4 Контроль исполнения

- Спавн с отдельной группой процессов (`process_group(0)` на Unix) —
  Ctrl+C в gateway шлёт SIGINT **группе** дочернего конвейера, а не только
  лидеру;
- Ожидание — поллинг `try_wait()` каждые 30 мс с проверкой флага
  `AtomicBool`, который поднимает обработчик SIGINT (`ctrlc`-крейт, уже в
  дереве): прерывание → SIGINT группе → 2 с grace → SIGKILL;
- stdout/stderr дочернего процесса — пайпы, читаются параллельно до капа;
- Код возврата: конвейер возвращает код последнего сегмента (как в POSIX).

## 5. Управление сервисным слоем: `service` и `attach`

### 5.1 Реестр сервисов

Реестр — статический, три сервиса (расширяемо):

| Имя | Команда запуска | Что держит |
|---|---|---|
| `mcp` | `poler-engine --mcp-http 127.0.0.1:8765` (токен через env `POLER_MCP_TOKEN` — НЕ в argv, чтобы не светился в `/proc/<pid>/cmdline`) | MCP-HTTP JSON-RPC (Bearer) |
| `weblens` | `poler-engine --web-lens 127.0.0.1:8765` (токен сам-managed в weblens-модуле, 0600) | WebLens-браузер + демон |
| `companion` | `poler-engine --auth-ui` | Auth Companion (окно логина Google) |

Состояние — файлы в `~/.local/state/poler-engine/services/` (переопределяется
переменной `POLER_STATE_DIR` — XDG-совместимость и тестовая изоляция):
`<name>.pid`, `<name>.json` (pid, bind/endpoint, token_path, started_utc),
логи — `~/.local/state/poler-engine/logs/<name>.log` (дочерний stdout/stderr
перенаправлен туда, не в терминал gateway). Спавн — `current_exe()`
(тесты подменяют через `POLER_GATEWAY_SVC_EXE`).

### 5.2 Жизненный цикл

- `service start <name>` — отклоняется, если pid жив (`kill(pid, 0)` и
  `/proc/<pid>` на Linux); спавн `current_exe()` с флагами сервиса,
  отвязанный от терминала (stdio → лог-файл), отдельная группа;
- `service status [name]` — таблица: имя, PID, alive, endpoint, uptime;
  liveness-проба MCP — TCP-connect на bind;
- `service stop <name>` — SIGTERM группе → grace 3 с → SIGKILL, pid-файл
  удаляется;
- `service restart <name>` — stop+start.

### 5.3 `attach <name>` — подключение к сессии

- `attach mcp` — интерактивный JSON-RPC-клиент поверх уже работающего
  MCP-сервера (ureq, Bearer из сервисного токен-файла 0600): `tools` —
  список инструментов, `call <tool> {json}` — вызов, сырая JSON-RPC строка —
  прямой запрос. Фактически это ручной агент поверх Service Substrate.
- `attach weblens|companion` — поток лога сервиса (tail -f до Ctrl+C) +
  сводка endpoint/токена. Это «подключение к сессии» в смысле наблюдаемости:
  живого tty у фонового сервиса нет by design (сервис стартовал отвязанным).

## 6. Сигналы и кроссплатформенность (Linux / macOS)

- **SIGINT (Ctrl+C)**: в REPL — сброс текущей строки (rustyline
  `Interrupted`); во время host-сегмента — SIGINT группе дочерних
  процессов через `kill(-pgid, SIGINT)` → grace 2 с → SIGKILL;
  во время engine-сегмента — флаг `INTERRUPT` проверяется между
  сегментами конвейера;
- **SIGWINCH** — rustyline `WindowResized`: перерисовка строки, цикл
  продолжается;
- **ANSI/VT100** — баннер и подсветка идут с цветовыми кодами только при
  `stdout_is_tty()` (уже канон из v0.20.0 grep); Ctrl+L — очистка экрана;
- **EOF (Ctrl+D)** — выход из gateway с сохранением истории;
- POSIX-only API изолированы за `#[cfg(unix)]` в `hostexec.rs`/`service.rs`
  (`process_group`, сигналы); `#[cfg(not(unix))]` ветка даёт понятную
  ошибку «gateway доступен на Linux/macOS» — Windows вне контракта v0.22.0.
- История команд — `~/.cache/poler-engine/gateway-history.txt` (до 5000
  строк, отдельная от внутреннего `--shell`, чтобы не смешивать контексты).

## 7. Интеграция с лицензионной моделью (Часть 2 v0.22.0)

- Баннер запуска gateway обязан показывать: версию, **тир лицензии**
  (Community/Pro/Enterprise/trial из Ed25519-гейта v0.18.0), название модели
  «POLER Custom Source-Available & Modification Disclosure License v1.0» и
  адрес раскрытия модификаций `dev@poler-engine.org` + ссылку на `TERMS.md`;
- `license` в REPL и `poler-engine --license` выводят один и тот же блок
  EULA-статуса (единый источник — `license::eula_notice()`), включая
  Notification Clause: любые модификации/форки/встраивание ядра в
  коммерческий продукт требуют уведомления авторов;
- Non-circumvention: обход Ed25519-гейта (патчинг бинарника, подмена
  публичного ключа, hook статуса) — нарушение лицензии и блокируется
  `verify_strict` (v0.21.1) на уровне проверки подписи.

## 8. Меры безопасности, унаследованные от аудита v0.21.1

- `OUTPUT_CAP` 16 МБ/поток — тот же лимит, что CDP `HTTP_BODY_CAP`;
- Секретные env-переменные не наследуются дочерними процессами (§4.3);
- Токен MCP-сервиса пишется в файл 0600 и никогда не печатается целиком
  (маска `pier_****`, первые 6 символов);
- `service stop` не трогает чужие PID (проверка имени процесса по
  `/proc/<pid>/comm` на Linux перед сигналом — защита от PID-reuse);
- Пути логов/pid-файлов — фиксированные под `$HOME`, не управляются
  вводом (нет инъекции пути).

## 10. Ограничения и роадмап

- Политика sandbox — статический анализатор строки; динамический аудит
  системных вызовов (seccomp-bpf на Linux, `sandbox-exec` на macOS) —
  кандидат в v0.23+ если появится нативная реализация без внешних
  зависимостей;
- Нет globbing (`*.rs` раскрывает shell пользователя — здесь нужен сам
  движок; globset уже в дереве, кандидат на v0.22.x);
- Нет управления задачами (`jobs`/`&`) — фоновые задачи = сервисы;
- R-3/R-4 аудита (развод `--disable-web-security`, миграция на
  `--remote-debugging-pipe`) остаются открытыми и не входят в v0.22.0;
- WebLens-сервис на macOS не стартует без дисплея — это штатное поведение
  (браузер оконный), демон продолжит работать.
