> Статус: реализовано в v0.22.0; sandbox-политика усилена в v0.22.1 по итогам
> adversarial-аудита (113-векторный корпус, 46 найденных и закрытых bypass-ов);
> v0.23.0 — интерактивные сессии и управление привилегиями: PTY-passthrough
> (TUI/IDE/агенты на живом терминале), Dynamic Workspace, гранулярный
> Sudo Privilege Gate с danger-режимом;
> v0.24.0 — Workspace Boundary Guard (доступ вне корня проекта — только
> по подтверждению владельца) и Mediated Agent Mode (PATH-shim медиация
> shell-вызовов PTY-агентов) — по итогам живой эксплуатации: агент внутри
> gateway свободно читал `/home` и писал в `/tmp`.
> Владелец архитектуры: POLER Engineering Core.
> Связанные документы: `TERMS.md` (лицензионная модель), `docs/native-retrieval-analysis.md`
> (grep/chunk), аудит v0.21.1 (`scripts/audit_stress.py --hardened`).

## 1. Концепция и место в системе

POLER Engine исторически состоит из двух поверхностей:

- **Нижний сервисный слой (Service Substrate)** — веб-GUI / Auth Companion,
  WebLens MV3, MCP-HTTP-сервер (`--mcp-http`), notebooklm-мост. Это фоновые
  сервисы: они держат сессии, токены и браузер, но не управляют рабочим
  процессом пользователя.
- **Прикладные CLI-режимы** — флаги `--grep`, `--chunk`, `--crawl`, `--impact`,
  `--shell` (внутренний REPL по web-index/notebooklm).

v0.22.0 добавляет **третий, верхний уровень** — **Terminal Gateway**
(`poler-engine --gateway`): единое окно терминала, в котором пользователь
работает и с движком, и с хостовой ОС, не покидая процесс. Gateway — это не
очередной режим поиска, а **рабочее место**: командная строка, из которой
управляется всё остальное, включая сам Service Substrate.

```
┌────────────────────────────────────────────────────────────┐
│  Terminal Gateway (REPL, --gateway)  ← ВЕРХНИЙ УРОВЕНЬ      │
│  двойной контур исполнения + конвейеры + service/attach     │
├────────────────────────────────────────────────────────────┤
│  Engine Native: search · grep · chunk · crawl · impact ·    │
│  nlm · notes · sources · gh/gl/gt/gix · benchmark · license │
├────────────────────────────────────────────────────────────┤
│  Service Substrate (НИЖНИЙ СЛОЙ): MCP-HTTP · WebLens ·     │
│  Auth Companion — управляются из gateway: service/attach    │
└────────────────────────────────────────────────────────────┘
```

## 2. Модель исполнения — двойной контур с приоритетом движка

Каждая строка ввода парсится в **конвейер** (сегменты через `|`), затем каждый
сегмент классифицируется ровно одним из двух контуров. Порядок проверки —
строгий, приоритет движка не обходится наличием одноимённого бинарника в PATH
(у пользователя почти всегда есть `/bin/grep` — но внутри gateway `grep` всегда
означает POLER Native Grep; это осознанное решение, подтверждённое бенчмарком
v0.21.0: 3.3 мс против 6.3 мс у ripgrep при полной полноте).

**v0.23.0**: поверх двух контуров добавлен третий канал — **PTY Passthrough**
(§6.1): интерактивные TUI/IDE/CLI-агенты (`vim`, `htop`, `agy`…) получают
настоящий псевдотерминал. Это не третий «класс» команд, а альтернативный
транспорт для контура 2: вердикт sandbox выносится по той же команде ДО спавна.

### Контур 1 — Engine Native (Приоритет 1)

Команда исполняется **внутри процесса движка**, без спавна внешних процессов.

Распознаётся по первому токену сегмента (опциональный префикс `poler` /
`poler-engine` срезается: `ls | poler chunk` ≡ `ls | chunk`):

| Команда | Реализация |
|---|---|
| `search` / `web`, `stats`, `nlm`, `notes`, `sources`, `sync`, `set`, `crawl`, `impact`, `gh`, `gl`, `gt`, `gix` | делегация в `shell::commands::dispatch` (внутренний REPL v0.15+, тот же код — один источник правды) |
| `grep PATTERN [--regex] [-i] [-A N] [-B N] [--count] [--list] … [--stdin]` | `retrieval::grep_run` + `render_text` (v0.20.0); `--stdin` — поиск по буферу из пайпа вместо файлов |
| `chunk [PATH] [--size N] [--overlap N] [--json] [--stdin]` | `retrieval::chunk_document` (v0.20.0); без PATH и в конвейере — чанкование stdin |
| `benchmark [--json PATH]` | `bench::run_suite` (v0.21.0) |
| `service start/stop/status/attach`, `attach` | §5 |
| `license`, `cd`, `pwd`, `clear`, `help`, `version`, `quit` | служебные команды gateway |
| `weblens [start/stop/status]` | сахар над `service` (WebLens — сервис) |

### Контур 2 — Controlled Host OS Proxy (Приоритет 2)

Всё, что не опознано как команда движка, исполняется **в хостовой ОС**
(Linux/macOS) через `std::process::Command` — но строго через
**Sandboxed OS Subshell** (§4): политика безопасности → контролируемый спавн →
кап вывода → таймаут → перехват SIGINT. Явный синтаксис принуждения: `!cmd`
или `host cmd` (например `!grep`, чтобы вызвать системный grep, а не движковый).

### Почему не «спавнить настоящий shell»

`sh -c "<строка>"` отдал бы строку на парсинг `/bin/sh` со всеми его
возможностями (подстановки, `$(...)`, бесконечная рекурсия), и sandbox свёлся
бы к проверке исходного текста. Вместо этого gateway сам токенизирует строку
(кавычки `'…'`/`"…"` поддерживаются, подстановки — нет) и запускает бинарник
**напрямую** (`execvp`-семантика), без промежуточного shell. Это устраняет
целый класс инъекций: `echo $(rm -rf /)` не исполняется вовсе — токен `$(rm…`
просто не найден как программа.

## 3. Конвейеры (pipes)

Сегменты конвейера нумеруются слева направо; вывод каждого сегмента (строка)
становится stdin следующего. Смешивание контуров разрешено в любом порядке:

```
ls -la src/ | chunk --size 200          # host → engine: чанкование вывода ls
cat src/main.rs | impact main           # host → engine: impact по символу
grep "fn " --stdin | wc -l              # engine → host: подсчёт движкового grep
cat README.md | chunk --size 300 | grep POLER --stdin --count
```

Правила:
- Engine-сегмент в середине/конце конвейера получает данные предыдущего
  сегмента в `stdin: Option<String>`.
- `grep`/`chunk` поддерживают флаг `--stdin` (в конвейере включается
  автоматически, флаг — для явности).
- `impact SYMBOL` в конвейере: код из stdin пишется во временный файл
  (`std::env::temp_dir()`), для него строится SymbolTable, отчёт печатается
  в stdout конвейера.
- Редирект `>` / `>>` / `2>` применяется к финальному выводу конвейера.
- `cd`/`pwd`/`set`/`service`/`license`/`quit` не участвуют в конвейерах
  (ошибка парсинга — как в bash для builtin в pipe, где это осмысленно).

## 4. Sandbox OS Subshell — политика безопасности

### 4.1 Категории решений

`Policy = Allow | Confirm(reason) | Block(reason)`:

- **Block** — деструктивные/системные операции, отказ сразу, без вопросов:
  - `rm` с `-r`/`-f` по корневым/системным целям (`/`, `/usr`, `/etc`,
    `/bin`, `/sbin`, `/lib*`, `/boot`, `/sys`, `/proc`, `/dev`, `/var`,
    `/home` верхнего уровня, `~` целиком, сам cwd `.`/`..`);
  - форк-бомбы — сырой скан строки на `:(){` (варианты с пробелами
    нормализуются) в любом месте конвейера, включая `bash -c '…'`;
  - `dd` с `of=/dev/…`, `mkfs*`, `wipefs`, `fdisk`, `parted`, `sfdisk`;
  - `shutdown`, `reboot`, `halt`, `poweroff`, `init 0/6`, `systemctl
    poweroff/reboot`;
  - редиректы в блочные/системные устройства (`> /dev/sd*`, `> /dev/nvme*`,
    `> /dev/disk*`) и в системные каталоги (`> /etc/…`, `> /boot/…`,
    `> /sys/…`, `> /proc/…`);
  - `chmod -R`/`chown -R` по системным корням;
  - удалённое исполнение `curl … | sh|bash` / `wget … | sh|bash`;
  - `mv`/`cp` с целью в `/dev`, `/sys`, `/proc`.
- **Confirm** — интерактивное подтверждение yes/no (в non-tty и в конвейере
  без `--yes` — отказ): `sudo`/`su`/`doas`/`pkexec` (эскалация прав);
  `rm` с рекурсией по НЕсистемным путям (показываем цели); `dd` без
  `/dev`-цели; `kill -9` не-своих процессов не поддерживаем — kill вообще
  вне gateway (используйте service stop).
- **Allow** — всё остальное: `ls`, `cat`, `git`, `cargo`, `python`, …

### 4.2 Честная threat model

Sandbox gateway — **политический** (userspace-фильтр), а не ядровый
(seccomp/namespace/sandbox-exec не подключаются — принцип нуля новых
зависимостей движка). Что это значит:

- Гарантируется: ни одна строка не достигает exec без классификации;
  разбор делаем мы, а не `/bin/sh`; спавн — прямой (`Command`, без shell);
  вывод ограничен (`OUTPUT_CAP` = 16 МБ на поток, как CDP-кап из аудита
  v0.21.1); таймаут стены (`HOST_TIMEOUT` = 120 с по умолчанию,
  `set hosttimeout N`); переменные окружения фильтруются (см. 4.3).
- НЕ гарантируется: изоляция эксплойта самого запускаемого бинарника
  (злонамеренная программа обходит любые пользователю доступные механизмы
  своей жертвы) — для этого нужны ядровые песочницы, и это явно указано
  как ограничение. Gateway защищает от **ошибок пользователя**
  (rm -rf по неверному пути, случайный fork-bomb из туториала, слив
  секретов в дочерние процессы) и от «уверенного» ИИ-агента, замкнутого
  в шлюзе, а не от целенаправленного малваре.

### 4.2.1 Hardening v0.22.1 — adversarial-аудит sandbox

Методика: корпуc из 113 векторов (классы A–S) прогоняется через
`examples/sandbox_probe` — пробник, вызывающий только классификатор
(`sandbox::judge_pipeline`) без исполнения; вердикты сверяются с ожиданиями
(скрипт `scripts/gateway_audit.py`); затем живая E2E-батарея через реальный
REPL (`scripts/gateway_attack_e2e.py`). Против v0.22.0 корпус выявил
**46 bypass-векторов** в 12 классах — все закрыты в v0.22.1:

| Класс | Вектор | Правило v0.22.1 |
|-------|--------|-----------------|
| B | `rm -fr /usr` (порядок флагов) | кластерный разбор коротких флагов: любой флаг rm с `r`/`R` = рекурсия |
| C | `env`/`nohup`/`nice`/`timeout`/`time`/`watch`/`strace` + rm | разворачивание обёрток до реальной команды (до 8 уровней) |
| D | `find / -delete`, `find / -exec rm …` | анализ путей поиска + внутренней команды -exec |
| E | `… \| xargs rm -rf` | внутренняя команда xargs классифицируется как сегмент |
| F | `python3 -c "…os.system('rm -rf /usr')…"`, `node -e`, `perl -e` | скан кода интерпретаторов на деструктивные паттерны (fail-closed) |
| G | `… \| sh`, `… \| base64 -d \| sh`, `echo x \| python3` | запрет исполнения ПОТОКА конвейера как кода (shell всегда; интерпретатор — без `-c`/файла) |
| H | `f(){ f\|f& };f` (без двоеточия) | обобщённая сигнатура форк-бомбы: `(){` + `&` + `\|` |
| I | `curl -o /etc/…`, `wget -O /etc/…` | цели вывода fetcher проходят редирект-анализ |
| J | `cp`/`mv`/`install`/`rsync`/`tar -C`/`truncate`/`shred`/`dd of=` в `/etc` | единый write-target-анализ всех файловых утилит |
| K | `su -c "rm -rf /usr"` (payload одним токеном) | флаттенинг кавычек в judge_privilege + судья по словам |
| L | `kill -9 1`, `kill -9 -1` | PID 1 / «все процессы» — Block; `killall`/`pkill` — Confirm |
| M | `nc -e /bin/sh …`, `socat EXEC:…`, `/dev/tcp` | reverse shell — Block (сырой скан + судья сетевых утилит) |
| N | `ln -s /etc/passwd pwn; echo x > pwn` | цели записи каноникализируются (realpath — симлинк-прокси раскрывается); проверяется и в чисто движковых конвейерах |
| O | `env LD_PRELOAD=… ls` | env-инъекции (LD_PRELOAD/PYTHONPATH/BASH_ENV/PATH…) — Block |
| R | `ssh host 'rm -rf /'` | удалённая команда судится как локальная |

Дизайн-инвариант: **fail-closed** — сомнительное блокируется/подтверждается,
легитимный workflow не страдает (контрольный набор: `cat data.csv |
python3 process.py`, `ls \| xargs grep`, `curl -o page.html …`, `find src
-name '*.rs'`, `nice -n 5 ls`, `tar -xzf release.tar.gz` — все Allow).
Полный корпус и оба скрипта — в репозитории; регрессии зафиксированы
unit-тестами `src/gateway/sandbox.rs` (классы B–R).

### 4.3 Контроль окружения дочерних процессов

Дочерним процессам передаётся **минимальное окружение**: `PATH`, `HOME`,
`LANG`, `LC_*`, `TERM`, `TMPDIR` и полностью унаследованный
`POLER_*`-неймспейс **кроме** секретов. Вырезаются все переменные, чьи имена
содержат `TOKEN`, `SECRET`, `PASSWORD` или заканчиваются на `_KEY`/`_KEYS`.
Дополнительно выставляется `POLER_GATEWAY=1` (дочерний процесс может
детектировать, что он в субшелле). Полный набор окружения — через
`set hostenv full` (по умолчанию `filtered`; изменение фиксируется в
строке статуса). Обоснование: рефреш-токены Google и MCP-токен живут в
файлах 0600 (аудит v0.21.1), но если пользователь экспортировал секрет в
env основного процесса — он не должен утекать в каждый `ls`.

### 4.4 Контроль исполнения

- Спавн с отдельной группой процессов (`process_group(0)` на Unix) —
  Ctrl+C в gateway шлёт SIGINT **группе** дочернего конвейера, а не только
  лидеру;
- Ожидание — поллинг `try_wait()` каждые 30 мс с проверкой флага
  `AtomicBool`, который поднимает обработчик SIGINT (`ctrlc`-крейт, уже в
  дереве): прерывание → SIGINT группе → 2 с grace → SIGKILL;
- stdout/stderr дочернего процесса — пайпы, читаются параллельно до капа;
- Код возврата: конвейер возвращает код последнего сегмента (как в POSIX).

## 5. Управление сервисным слоем: `service` и `attach`

### 5.1 Реестр сервисов

Реестр — статический, три сервиса (расширяемо):

| Имя | Команда запуска | Что держит |
|---|---|---|
| `mcp` | `poler-engine --mcp-http 127.0.0.1:8765` (токен через env `POLER_MCP_TOKEN` — НЕ в argv, чтобы не светился в `/proc/<pid>/cmdline`) | MCP-HTTP JSON-RPC (Bearer) |
| `weblens` | `poler-engine --web-lens 127.0.0.1:8765` (токен сам-managed в weblens-модуле, 0600) | WebLens-браузер + демон |
| `companion` | `poler-engine --auth-ui` | Auth Companion (окно логина Google) |

Состояние — файлы в `~/.local/state/poler-engine/services/` (переопределяется
переменной `POLER_STATE_DIR` — XDG-совместимость и тестовая изоляция):
`<name>.pid`, `<name>.json` (pid, bind/endpoint, token_path, started_utc),
логи — `~/.local/state/poler-engine/logs/<name>.log` (дочерний stdout/stderr
перенаправлен туда, не в терминал gateway). Спавн — `current_exe()`
(тесты подменяют через `POLER_GATEWAY_SVC_EXE`).

### 5.2 Жизненный цикл

- `service start <name>` — отклоняется, если pid жив (`kill(pid, 0)` и
  `/proc/<pid>` на Linux); спавн `current_exe()` с флагами сервиса,
  отвязанный от терминала (stdio → лог-файл), отдельная группа;
- `service status [name]` — таблица: имя, PID, alive, endpoint, uptime;
  liveness-проба MCP — TCP-connect на bind;
- `service stop <name>` — SIGTERM группе → grace 3 с → SIGKILL, pid-файл
  удаляется;
- `service restart <name>` — stop+start.

### 5.3 `attach <name>` — подключение к сессии

- `attach mcp` — интерактивный JSON-RPC-клиент поверх уже работающего
  MCP-сервера (ureq, Bearer из сервисного токен-файла 0600): `tools` —
  список инструментов, `call <tool> {json}` — вызов, сырая JSON-RPC строка —
  прямой запрос. Фактически это ручной агент поверх Service Substrate.
- `attach weblens|companion` — поток лога сервиса (tail -f до Ctrl+C) +
  сводка endpoint/токена. Это «подключение к сессии» в смысле наблюдаемости:
  живого tty у фонового сервиса нет by design (сервис стартовал отвязанным).

## 6. PTY Passthrough, Dynamic Workspace и Privilege Gate (v0.23.0)

### 6.1 PTY Passthrough — контур 3 для TUI/IDE/агентов

**Проблема.** Полноэкранные приложения (vim, htop, less, tmux, CLI-агенты
agy/claude/codex) требуют настоящего псевдотерминала: на пайпах stdin/stdout
они зависают или отказываются рендерить (живой кейс эксплуатации: `agy` внутри
шлюза v0.22.1 ждал PTY).

**Реализация** — `hostexec::run_pty` (Linux):

- master-PTY через `posix_openpt`/`grantpt`/`unlockpt`/`ptsname_r` — тонкие
  `extern "C"`-обёртки над libc (как `kill(2)` в v0.22.0): ноль новых
  зависимостей;
- спавн `std::process::Command` со slave-PTY как stdio (три дескриптора),
  `pre_exec`: `setsid()` + `ioctl(0, TIOCSCTTY)` — slave становится
  управляющим терминалом новой сессии (job control работает);
- хост-терминал в raw mode (crossterm — уже в дереве), возврат — RAII-guard;
- насос на `poll(2)`: stdin→master, master→stdout live + транскрипт
  (кап `OUTPUT_CAP` — защита памяти); stdin качается ТОЛЬКО если он
  настоящий TTY — иначе PTY-сессия съела бы чужой пайп (скрипты, тесты);
- ресайз окна: `TIOCSWINSZ` на master при изменении размера хост-терминала
  (проверка раз в ~500 мс) — TUI-приложения перерисовываются корректно;
- Ctrl+C в raw mode идёт байтом 0x03 → line-discipline слейва сам
  превращает его в SIGINT foreground-группе потомка (классика PTY);
- wall-timeout НЕ применяется: интерактивной сессией управляет владелец
  (выход из TUI = конец сессии); код возврата пробрасывается.

**Роутинг** (`dispatch::exec_line`, до классификации контуров):

- авто-PTY в интерактиве: известный TUI-список (vim/nano/htop/less/tmux/
  lazygit/agy/claude/…) и bare-REPL (`python3` без аргументов); только
  одиночный сегмент без редиректа;
- принудительно — префикс `pty <cmd>` (без ограничений на аргументы);
- `!cmd`/`host cmd` — прежнее поведение без PTY (эскейп-хэтч);
- в неинтерактиве TUI не запускается: честный отказ «требует настоящего
  терминала» вместо зависания.

**Инвариант безопасности не меняется**: PTY — это только канал I/O. Вердикт
sandbox судится по той же команде ДО спавна (`pty rm -rf /` → Block;
интерпретаторные payload'ы — INTERP_DANGER-скан; Confirm — через те же
ворота с sudo-лизингом). macOS — graceful degradation: ioctl-константы
платформозависимы, поэтому честное сообщение «поддерживается на Linux»
вместо непроверенного кода.

### 6.2 Dynamic Workspace — корень проекта

- `workspace [PATH]` — показать/переключить корень: меняет `state.cwd` И
  process-cwd синхронно → движковые `grep`/`chunk`/`search`, хостовые
  команды и подпроцессы (включая агентов в PTY) работают от одного корня;
  промпт обновляется автоматически;
- `cd PATH` — быстрая навигация с той же синхронизацией;
- юнит-тесты глобальный cwd не мутируют (флаг `sync_cwd` включается только
  в живом REPL) — параллельные тесты не флакают.

### 6.3 Sudo Privilege Gate — три уровня доверия

| Уровень | Как включается | Поведение |
|---|---|---|
| **One-shot** (по умолчанию) | `sudo <cmd>` в интерактиве | подтверждение на **/dev/tty** — исполняется РОВНО ОДНА команда, права мгновенно «сбрасываются» |
| **Session Lease** | `grant sudo 5m|90s|2h` (только интерактив, кап 60 мин, `grant sudo off` — отзыв) | privilege-Confirm не спрашивается до сгорания таймера |
| **Danger Override** | `--dangerously-allow-all` при старте или `set sandbox off` (интерактив + подтверждение на /dev/tty) | sandbox полностью отключён: красный баннер, маркер ☠DANGER в промпте, ответственность оператора |

Принципы:

- **Zero Silent Escalation**: подтверждения привилегий читаются с `/dev/tty`
  (реальный терминал владельца), а не из stdin — пайп-агент физически не
  может ответить за человека; `grant sudo` и `set sandbox off` из
  неинтерактива — отказ (⛔);
- **«Разрешение действия ≠ снятие фильтра»**: лизинг и подтверждение
  поднимают ТОЛЬКО Confirm-ворота эскалации — Block-вердикты (wiper'ы,
  `dd of=/dev/*`, reverse shell, `…|sh`) блокируются ВСЕГДА, даже под
  sudo с активным лизингом (тест `grant_lease_does_not_bypass_destructive`);
- **Осознанный danger**: в danger-режиме вердикты вычисляются, но не
  применяются — каждое потенциально заблокированное действие
  сопровождается stderr-предупреждением `⚠ DANGER` (видимость без
  блокировки); `set sandbox on` возвращает защиту в любой момент;
- `set sandbox status` — сводка режима + остаток лизинга; `grant` —
  статус лизинга.

### 6.4 Workspace Boundary Guard (v0.24.0) — граница корня проекта

Живой кейс из эксплуатации v0.23.0: владелец запустил gateway в
`~/Стільниця/test_user_project`, агент внутри свободно выполнил
`ls -la /home/vitalij` и `echo x > /tmp/poler_test.txt` — sandbox
классифицировал их как «не деструктивные» и пропустил. v0.24.0
закрывает этот класс: **любое обращение к пути вне корня workspace —
Confirm `[y/N]`** (владелец видит точный путь; неинтерактив/пайп-агент —
отказ ⛔).

Механика (`sandbox.rs::WsGuard` + `judge_*_ws`):

- **Граница** = корень workspace (`state.ws_root`), отдельно от cwd
  (`cd` в подкаталог — свободен, `cd ..` назад — тоже; выход ЗА
  границу — Confirm, подтверждённый выход переносит границу);
- судятся ВСЕ контуры доступа к путям: аргументы хостовых сегментов,
  цели редиректов (`>`, `>>`, `2>`), `cp/mv/dd/curl -o`-цели,
  файл-аргументы движковых команд (`grep/chunk/impact/…`),
  код интерпретаторов (`python3 -c "open('/etc/x')"` — абсолютные
  пути извлекаются из строки кода), argv[0] вне системных корней
  (`/tmp/evil.sh`), «голые» имена-симлинки (`cat leak`, где
  `leak → /etc`);
- **payload шелла разбирается как настоящая командная строка**
  (`judge_shell_payload`): сплит `&&`/`||`/`;`/`&`/переводы строк вне
  кавычек, подстановки `$(…)`/бэктики/`<(…)` вынимаются и судятся
  рекурсивно (до глубины 4), каждая часть — через полный конвейерный
  судью с кавычками и пайпами; `bash -c "ls && rm -rf /usr"` → Block,
  `bash -c "cat '/etc/passwd'"` → Confirm; неразбираемое/незакрытое —
  Block (fail-closed);
- разбор путей: канонизация с раскрытием симлинков (несуществующий
  хвост — родитель+имя, край — лексическая нормализация `..`);
  `~` → HOME; относительные — от cwd; сравнение границ — по компонентам
  (`/ws/x2` не внутри `/ws/x`); URL (`scheme://`) — не путь;
  `/dev/null|tty|zero|stdin|stdout|stderr|…` — не граница;
- **allowlist владельца**: `allow <PATH>` (только интерактив! из пайпа —
  ⛔) — сессионное исключение для пути вне корня; `allow` — список,
  `allow clear` — сброс. **Инвариант: allowlist смягчает только
  boundary-Confirm — Block-вердикты (`rm -rf /`, `dd of=/dev/*`,
  reverse-shell, запись в `/etc`) действуют ВСЕГДА** (тест
  `boundary_allowlist_softens_only_boundary`);
- `cd <вне>`/`workspace <вне>` — Confirm (подтверждённый выход
  переносит границу; неинтерактив — отказ: scripted-агент не может
  уводить корень);
- `set autoyes on` (владелец) пропускает boundary-Confirm, как и прочие
  Confirm; danger-режим отключает границу вместе со всем sandbox.

### 6.5 Mediated Agent Mode (v0.24.0) — PATH-shim медиация агентов

PTY-агент (`agy`, `claude`, `codex`, `gemini`, `aider`…) — отдельный
процесс со СВОИМИ инструментами: его Bash-tool дергает шелл напрямую,
мимо судьи шлюза. Ядровая песочница (seccomp/landlock) вне философии
движка — медиация построена на честном best-effort PATH-shim:

1. При запуске агента шлюз кладёт в `~/.poler-engine/shim/` двухстрочные
   обёртки для `bash/sh/zsh/dash/ksh/fish` и ставит каталог ПЕРВЫМ в
   `PATH` (и в `$SHELL`) процесса агента;
2. если агент разрешает shell через PATH/$SHELL — вызов приходит в
   hidden-команду `poler-engine __gateway-shim <shell> -c <payload>`,
   которая судит payload тем же судьёй (`judge_shell_payload` +
   граница `POLER_WORKSPACE` + allow-файл `POLER_SHIM_ALLOW`);
3. вердикты в медиации: **Allow** → исполняется; **Block/Confirm** →
   отказ с кодом **126** и объяснением агенту. Подтвердить агент
   не может В ПРИНЦИПЕ: выход за границу расширяет только владелец
   (`allow <путь>` в шлюзе + перезапуск агента); sudo внутри агента —
   всегда отказ;
4. потоковые шеллы (`bash`, `bash -i`, `python3` без кода в аргументах,
   `exec bash`, `nohup sh -s` внутри payload) — код пришёл бы по stdin
   мимо фильтра → отказ (в REPL они безвредны: stdin — Stdio::null);
5. каждый вызов пишется в журнал; после выхода агента шлюз печатает
   телеметрию (сколько вызовов перехвачено/отклонено и почему);
   **ноль перехваченных вызовов = предупреждение**: агент вызывает
   shell по абсолютному пути — его команды НЕ фильтровались.

**Честные границы медиации** (важно понимать): агент, хардкодящий
`/bin/sh` (например, node child_process.exec), или делающий execve
мимо шелла, медиацией НЕ накрывается; произвольные syscall
userspace-фильтру не видны. Это не баг, а границы подхода — для
гарантированной изоляции нужен уровень ядра или контейнер (§6.6 —
реализовано в v0.25.0). Телеметрия всегда показывает реальное
состояние — честность важнее иллюзии защиты. Инструменты владельца
(vim/htop/less) не медиируются: за терминалом сам человек.

### 6.6 Container Jail (v0.25.0) — жёсткая Docker-изоляция контуров 2/3

Живой кейс, закрывший класс: агент в PTY-контуре работает на хосте
напрямую (его Bash-tool — отдельный процесс с собственным `/bin/bash`);
PATH-shim медиация (§6.5) перехватывает вызовы через PATH/$SHELL, но
хардкод `/bin/sh` и прямой execve не накрывает — и userspace-фильтр в
принципе не может дать гарантию. Ответ v0.25.0 — **физическая
изоляция**: шлюз поднимает Docker-контейнер («box») и исполняет
контур 2 (host-os-proxy) и контур 3 (pty-passthrough) ВНУТРИ него.

Управление — команда `box`:

```
box on [image=IMG] [net=bridge|none] [user=me|root] [mem=2g] [pids=512] [wsro=0|1]
box status | box off | box shell
```

Модель изоляции контейнера `poler-box-<fnv1a8(ws_root)>`:

- **Монтировки**: `/workspace` ← корень workspace (rw; `wsro=1` —
  read-only для аналитических агентов) и `/home/poler` ← персистентный
  каталог `~/.local/share/poler-engine/box/<name>` (конфиги/токены
  агентов переживают `box off/on`). БОЛЬШЕ НИЧЕГО с хоста не
  смонтировано: `/home`, `/etc`, `/tmp` хоста агенту не видны — там
  контейнерные ФС;
- **Hardening**: `--cap-drop ALL`, `--security-opt no-new-privileges`,
  `--init` (tini — зомби-реапер), `--memory/--memory-swap` (swap = mem,
  лимит не обойти свопом), `--pids-limit` (второй эшелон анти-форк-бомбы),
  `--stop-timeout 2`; **docker-сокет НЕ пробрасывается** — агент внутри
  не может управлять демоном;
- **Юзер**: по умолчанию `uid:gid` владельца — файлы в /workspace
  остаются собственностью хозяина; `user=root` — root ВНУТРИ контейнера
  (установка пакетов), что безопасно для хоста при отброшенных
  capabilities и отсутствии сокета;
- **Сеть**: `bridge` (агентам нужен API LLM) или `none` (полная
  тишина); `net=host` отвергается на парсинге — открывает хост;
- **Образ**: по умолчанию `debian:bookworm-slim`; для агентов — свой
  (`box on image=node:22-slim`, образ с предустановленным agy и т.п.);
  `docker run` тянет отсутствующий образ (таймаут 600 с).

Исполнение: host-сегменты уходят как `docker exec -i -w <cwd> -e HOME
-e TERM <name> <argv…>`, PTY-сессии — `docker exec -it …` (наш PTY-насос
качает байты в docker-клиент, тот — в контейнерный tty; ресайз и Ctrl+C
пробрасываются штатно). argv передаётся насквозь без `/bin/sh` — тот же
принцип, что у hostexec. `box shell` — интерактивный шелл внутри
(константная команда `sh -c 'exec bash || exec sh'`).

**Вердикт-плоскость в jail-режиме** (инвариант «вердикт до исполнения»
сохранён, судья видит исходные токены ДО обёртки):

- деструктив (rm -rf /, dd of=/dev/*, reverse-shell…) — Block ВСЕГДА:
  jail не ослабляет Block-вердикты (внутри контейнера живые данные
  workspace через rw-монтировку);
- **логическая граница workspace для exec-плоскости снимается** — её
  заменяет контейнер: `cat /etc/passwd` в jail читает контейнерный
  /etc/passwd (одноразовый), хостовые пути агенту просто не существуют;
- redirect-цели (`> файл`) судятся с ПОЛНОЙ границей ВСЕГДА — файл
  пишет сам движок НА ХОСТЕ (finish()), контейнер эту запись не
  изолирует; движковые файл-команды (grep/chunk/…) — аналогично:
  движок читает файлы на хосте;
- управление docker/podman-демоном из gateway при активном jail —
  Confirm (`docker run -v /:/host` ломает изоляцию); в неинтерактиве —
  отказ: scripted-агент не управляет демоном;
- при `box on` активные PATH-shim медиации агентов отключаются —
  в контейнере они бессмысленны (shim-файлы хоста не смонтированы),
  физическая изоляция заменяет логическую фильтрацию.

Lifecycle: контейнер именован по корню workspace — `box on` в новой
сессии принимает уже работающий контейнер (конфигурация читается из
docker-labels — источник истины сам контейнер); выход из gateway НЕ
убивает box (`docker -d`), о чём REPL честно напоминает при quit.
`box off` — `docker rm -f` (workspace и home на хосте не тронуты).
`cd`/`workspace` с переносом корня при активном jail предупреждает:
контейнер продолжает монтировать прежний корень (`box off && box on`).

**Честные границы** (по-прежнему без иллюзий): rw-монтировка workspace
означает, что агент ПО ЗАМЫСЛУ пишет в рабочую область (это его работа);
если нужен анализ без записи — `wsro=1`. Контейнер не защищает от
потребления CPU/сети (лимиты mem/pids есть, CPU-shares — роадмап).
Гарантии держатся на модели изоляции Docker (namespaces/cgroups) при
отсутствии привилегированных монтировок; `user=root` внутри даёт агенту
root над контейнером, но не над хостом. Требуется установленный и
запущенный docker-демон; без него `box on` честно отказывает, шлюз
работает в режиме v0.24 (workspace-guard + медиация).

## 7. Сигналы и кроссплатформенность (Linux / macOS)

- **SIGINT (Ctrl+C)**: в REPL — сброс текущей строки (rustyline
  `Interrupted`); во время host-сегмента — SIGINT группе дочерних
  процессов через `kill(-pgid, SIGINT)` → grace 2 с → SIGKILL;
  во время engine-сегмента — флаг `INTERRUPT` проверяется между
  сегментами конвейера;
- **SIGWINCH** — rustyline `WindowResized`: перерисовка строки, цикл
  продолжается;
- **ANSI/VT100** — баннер и подсветка идут с цветовыми кодами только при
  `stdout_is_tty()` (уже канон из v0.20.0 grep); Ctrl+L — очистка экрана;
- **EOF (Ctrl+D)** — выход из gateway с сохранением истории;
- POSIX-only API изолированы за `#[cfg(unix)]` в `hostexec.rs`/`service.rs`
  (`process_group`, сигналы); `#[cfg(not(unix))]` ветка даёт понятную
  ошибку «gateway доступен на Linux/macOS» — Windows вне контракта v0.22.0.
- История команд — `~/.cache/poler-engine/gateway-history.txt` (до 5000
  строк, отдельная от внутреннего `--shell`, чтобы не смешивать контексты).

## 9. Меры безопасности, унаследованные от аудита v0.21.1

- `OUTPUT_CAP` 16 МБ/поток — тот же лимит, что CDP `HTTP_BODY_CAP`;
- Секретные env-переменные не наследуются дочерними процессами (§4.3);
- Токен MCP-сервиса пишется в файл 0600 и никогда не печатается целиком
  (маска `pier_****`, первые 6 символов);
- `service stop` не трогает чужие PID (проверка имени процесса по
  `/proc/<pid>/comm` на Linux перед сигналом — защита от PID-reuse);
- Пути логов/pid-файлов — фиксированные под `$HOME`, не управляются
  вводом (нет инъекции пути).

- **E2E-смоуки**: живой `--gateway` в PTY, сценарий из приветственного
  баннера.

## 11. Ограничения и роадмап

- Container Jail (§6.6, v0.25.0) решает класс физической изоляции,
  но требует docker-демона; альтернатива без внешних зависимостей —
  Landlock (пути) / seccomp-bpf (syscalls) на уровне ядра — остаётся
  кандидатом для машин без docker; CPU-shares и cgroup-v2-тюнинг jail —
  кандидат v0.25.x;
- Mediated Agent Mode — best-effort на PATH/$SHELL (§6.5): абсолютные
  пути к шеллу и прямой execve мимо шелла медиацией не накрываются;
  телеметрия честно предупреждает о нулевом покрытии. При активном
  Container Jail медиация отключается — её заменяет контейнер (§6.6);
- Политика sandbox — статический анализатор строки; динамический аудит
  системных вызовов (seccomp-bpf на Linux, `sandbox-exec` на macOS) —
  кандидат в v0.24+ если появится нативная реализация без внешних
  зависимостей;
- Граница workspace не отслеживает write-then-execute (агент может
  записать скрипт внутрь ws и запустить его — содержимое файла судье
  не видно); смягчение — трекинг созданных файлов, кандидат в роадмап;
- PTY-passthrough — Linux-only (macOS — graceful degradation, §6.1);
- Нет globbing (`*.rs` раскрывает shell пользователя — здесь нужен сам
  движок; globset уже в дереве, кандидат на v0.23.x);
- Нет управления задачами (`jobs`/`&`) — фоновые задачи = сервисы;
- R-3/R-4 аудита (развод `--disable-web-security`, миграция на
  `--remote-debugging-pipe`) остаются открытыми и не входят в v0.23.0;
- WebLens-сервис на macOS не стартует без дисплея — это штатное поведение
  (браузер оконный), демон продолжит работать.
