# POLER Vault `.pvt` — спецификация формата v1

> Крипто-слой данных (M4.5 CDL, `docs/UNIFIED_ARCHITECTURE.md`).
> Реализация: `src/crypto/vault.rs` (Rust) поверх C-ABI моста к
> Zig-ядру PND v8.2 (`os/core/poler_core.zig`, фича `pnd-ffi`).

## 1. Назначение

Vault — **зашифрованный постоянный носитель памяти** для инструмента
POLER: любой поток пользователя (документы, логи терминала, история
чата, ответы ИИ, базы знаний) запечатывается в бинарный контейнер
`.pvt`, который:

- **нечитаем без ключа** (CBC-каскад PND v8.2, 256-битный ключ из
  парольной фразы, соль и итеративный KDF);
- **проверяем без ключа** на транспортную целостность (SHA-256
  шифротекста + FNV-1a64 заголовка) — битый git-sync/диск/передача
  видны до расшифровки;
- **аутентифицируется с ключом** (ключевой ланцюговий MAC, домен
  `POLER.PNDHASHER.VAULT_*`) — неверная фраза или подмена = отказ;
- **масштабируется потоково**: память O(1) при печати/вскрытии,
  рассчитан на данные от 500 КБ до сотен ГБ;
- **дружелюбен к git**: страницы 4096 Б выровнены, детерминизм при
  фиксированной соли (пере-печать не мусорит в истории), свежая соль
  при обычной печати (равенство файлов не течёт).

Философия (владелец): криптография в POLER — не только «спрятать от
хакера», но и **инструмент работы с данными**: детерминированная
трансформация, контентная адресация, целостность фактов.

## 2. Раскладка контейнера

```text
Страница 0 — заголовок (4096 Б, все числа little-endian):
  0x00  8   magic "POLERVLT"
  0x08  4   format_version = 1
  0x0C  4   flags (bit0 = FLAG_CONTENT_ID: поле content_id заполнено)
  0x10  4   kdf_iterations (≥ 10 000; default 100 000)
  0x14  4   epsilon шифра (нечётный, выводится из соли)
  0x18  32  salt — 8×u32 LE (свежая при каждой печати: /dev/urandom,
            фолбэк DRBG(время ⊕ pid))
  0x38  8   original_len — реальная длина открытого текста (байт)
  0x40  8   page_count — число страниц данных (= ceil(original_len/4096))
  0x48  32  inner_mac — цепной MAC (см. §4)
  0x68  32  outer_digest — SHA-256(страницы 1..N шифротекста)
  0x88  32  content_id — публичный контент-хеш (только при FLAG_CONTENT_ID,
            иначе нули; см. §5)
  0xA8  8   header_checksum — FNV-1a64 по байтам 0x00..0xA8
  0xB0..0x1000   нули (резерв под будущие версии)

Страницы 1..N — CBC-шифротекст:
  каждая ровно 4096 Б; открытый текст страницы дополняется нулями до
  4096 (реальная длина — из original_len); IV каждой страницы —
  детерминированная функция (salt, номер страницы), в файле не хранится.
```

Ключ шифра: `key = KDF(passphrase, salt, kdf_iterations)` — 256 бит
(`src/crypto/kdf.rs`, домен `POLER.VAULT.KDF.v1`: Φ-свёртка фразы ⊕
соль, затем `kdf_iterations` итераций полного шифра PND + DRBG-экстракция).
`epsilon = phi(salt[0] ⊕ salt[4]) | 1` — параметр шифра, хранится явно.

IV страницы `i`: `pndMix`-свёртка соли и номера (4 слова; доменная
константа `IV_EPSILON = 0x517CC1B7`). Свойства: детерминирован без
хранения, непредсказуем без соли, уникален в контейнере (тест
`page_ivs_unique`), страницы статистически независимы — это даёт
безопасное **параллельное шифрование страниц** (rayon, батчи по 128).

## 3. Печать / вскрытие (потоковые, O(1) памяти)

```text
seal(input, output, passphrase, opts):
  salt ← urandom (или фиксированная — детерминизм в пайплайнах)
  key ← KDF; epsilon ← phi(salt[0]^salt[4])|1
  зарезервировать страницу 0 нулями
  цикл батчей по 128 страниц:
    прочитать страницы (последовательно; хвост — нули)
    ЛУЧИ RAYON: CBC-зашифровать страницу; MAC-лист (см. §4);
      при opts.content_id — контент-лист (§5)
    последовательно: записать шифротекст, outer.update(ct),
      mac.update(лист), content.update(контент-лист)
  заголовок (inner_mac, outer_digest, content_id, длины) → страница 0

open(input, output, passphrase):
  разобрать заголовок (магия, версия, FNV, согласованность page_count)
  key ← KDF(фраза, salt, iterations)
  цикл батчей: ЛУЧИ RAYON: CBC-расшифровать + MAC-лист из шифротекста
    последовательно: записать реальные байты, mac.update(лист)
  ПРОВЕРКА: outer_digest (транспорт) и inner_mac (аутентичность) —
  любая не сошлась → отказ с точной причиной.
```

## 4. Ланцюговий MAC (inner_mac)

```text
leaf_i  = PndHasher_keyed(key, "POLER.PNDHASHER.VAULT_MAC.v1",
                          IV_i ‖ last_ct_block_i ‖ u64_le(i))
inner_mac = PndHasher_keyed(key, "POLER.PNDHASHER.VAULT_CHAIN.v1",
                            leaf_0 ‖ leaf_1 ‖ … ‖ leaf_{N−1})
```

- `last_ct_block_i` — последний 16-байтовый блок CBC-шифротекста
  страницы. CBC-сцепление делает его зависящей от ключа перестановкой
  ВСЕЙ страницы (любой бит открытого текста/IV меняет его) — лист
  покрывает страницу при стоимости одной компрессии вместо 256;
- номер в листе + порядок листьев в цепи связывают **позицию**
  (перестановка/усечение/приписывание страниц меняет inner_mac);
- лист считается в луче rayon из самого шифротекста — проверка MAC
  не требует расшифровки;
- подделка без парольной фразы невозможна (оба хеш-слоя ключевые);
  вероятность пролезтия при подмене ≈ 2⁻²⁵⁶.

## 5. content_id (опция, публичный)

`--memory-content-id` записывает в заголовок публичный контент-хеш:

```text
cleaf_i    = PndHasher("POLER.PNDHASHER.CONTENT.v1", page_real_i ‖ u64_le(i))
content_id = PndHasher(CONTENT, cleaf_0 ‖ cleaf_1 ‖ … ‖ cleaf_{N−1})
```

Назначение — **контентная адресация/дедупликация** между контейнерами
без ключа (идентичность данных видна по заголовку). Плата: публичный
хеш позволяет сверять догадки о содержимом (known-plaintext по хешу),
поэтому по умолчанию ВЫКЛЮЧЕНО. Дополнительная стоимость включения —
один проход публичного хеша по данным (параллелится лучами).

## 6. CLI (фича `pnd-ffi`)

```bash
# ключ: env POLER_VAULT_KEY (или --memory-key-env VAR), иначе строка из stdin
export POLER_VAULT_KEY="…"

poler-engine --memory-seal   PATH            # → PATH.pvt
poler-engine --memory-open   VAULT.pvt       # → VAULT (или --memory-out)
poler-engine --memory-verify VAULT.pvt       # без ключа: FNV + SHA-256
poler-engine --memory-info   VAULT.pvt       # метаданные без ключа

# опции печати:
#   --memory-out PATH        явный выход (по умолчанию не перезаписывает существующий)
#   --memory-content-id      публичный контент-хеш в заголовок
#   --memory-kdf-iters N     итерации KDF (default 100000, минимум 10000)
```

Синхронизация памяти через git: контейнер — обычный файл;
`git add/commit/pull/push` любого ремоу́та (GitHub/GitLab/Gitea/локальный
bare). Порядок рабочего цикла агента:

```bash
poler-engine --memory-seal session-logs.md          # запечатать
git add session-logs.md.pvt && git commit -m "memory" && git push
git pull && poler-engine --memory-verify session-logs.md.pvt   # проверка
poler-engine --memory-open session-logs.md.pvt      # вскрыть на новой машине
```

## 7. Производительность (честные замеры)

Микросхема ядра до/после оптимизаций M4.5 (побитово точных, см. §8):

| Метрика | до | после |
|---|---|---|
| lhcaStep | ~61 нс (лестница 32 бита) | ~0 (5 операций) |
| mixColumnsPnd | 4 полных GF-умножения | 6 xtime |
| S-box | 4×74 нс (по-байтно) | ~74 нс на слово (4-лейновый u64) |
| Блок шифра (ReleaseFast) | 15.5 мкс | **6.2 мкс** |

End-to-end (песочница 2 ядра, ReleaseSafe, KDF 100k = 0.62 с в каждом
запуске — фиксированная стоимость):

| Данные | seal | open |
|---|---|---|
| 500 КБ | 0.74 с | 0.76 с |
| 5 МБ | 2.06 с (2.4 МБ/с) | 2.08 с |
| 50 МБ | 15.3 с (3.3 МБ/с) | 15.7 с |

Масштабирование — по ядрам (страницы независимы, rayon): ожидание на
8–16 ядрах ≈ 15–40 МБ/с. Следующие рычаги (бэклог): Canright
composite-field S-box (ещё ~2.5×), батч-инлайн CBC без Vec-конверсий.

## 8. Верификация

- Zig: 33/33 (включая 3 исчерпывающих теста эквивалентности
  оптимизаций: lhca 10 млн состояний + 2^16, 4-лейновый S-box
  10 млн слов + все 256 в каждой лейне, xtime-микс);
- **Golden-векторы: 54 626 — BIT-FOR-BIT IDENTICAL** до и после всех
  оптимизаций (регенерация `tools/verifiers/zig_probe/golden_dump.zig`,
  `diff` пуст) — выходные биты ядра не изменились ни на одном входе;
- Rust: `cargo test --lib --features pnd-ffi` — 1061/1061
  (roundtrip всех размеров, tamper шифротекста/заголовка, неверный
  ключ, обрыв, детерминизм, соль, content-id, границы IV);
- Python: `verify_pnd_full.py --sections golden` (CI).

Открытые вопросы (бэклог аудита): формальный анализ конструкции
MAC-листа из CBC-хвоста (интуитивно — CBC-MAC с детерминированным
IV из соли + домен-разделённые ключевые хеши); P1-пункты аудита
Шнайера (RSA-blinding, RDRAND-подмешивание, доменный KDF) — без изменений.
